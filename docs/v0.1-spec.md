# Neodermo v0.1 spec

This file is the product spec for v0.1. Current `main` shows what has been implemented.

## Product

Neodermo is a mobile-first wound-care journal: Patient → Wound → Assessment, with a PatientStay linking each patient to an establishment over a dated period. Photos are planned; the login API is implemented. Only observation time is a required clinical assessment field. Establishment and location are navigation context, not clinical observations. The nurse decides what else to document.

Develop and demonstrate with fictional cases. Real nursing usefulness is the product intent. This is a learning project, not a clinical system.

v0.1 is a local desktop browser cut of that product. Learning the complete agreed authentication lifecycle takes priority over the earlier time box. No phone testing, native tooling, AI, or public hosting in this release. Keep the Flask HTTP/JSON API and data model reusable for a later Android client. React web screens do not automatically become that client.

## Records

| Record | Fields |
| --- | --- |
| Establishment | Generated UUID and required name; optional address, phone number, email, and notes |
| Patient | Generated UUID, readable reference, and one required name; optional birth date and sex; allergy text; creation/update time; nullable archive time reserved for later |
| Patient stay | Generated UUID; patient and establishment IDs; optional service, room, and bed; required start date and optional end date |
| Wound | Generated UUID; patient ID; optional placement, treatment start date, and wound type; creation time and nullable closure time (`closed_at`) |
| Assessment | Generated UUID; wound ID; observation date/time; optional evolution, observations, care performed, expected outcome, exudate level, wound colour, odour, infection, length/width/depth in cm, remarks, three multi-select finding lists, and later one photo storage key; server creation time |

- Evolution is improved / unchanged / worsened, with no default. Blank means not recorded.
- Allergies are one text field. An empty value means no allergies; there is no separate allergy status.
- Sex is male or female when recorded; blank means not recorded. Age is derived from the optional birth date when needed. Weight is not recorded.
- Exudate level is dry / moist / wet; wound colour is red / black / yellow; odour is none / mild / strong. These are single choices per assessment.
- Wound edges may include hollowed, maceration, hyperkeratosis, eczema, epithelialization, or normal. Wound-bed tissue may include layer, epithelialization, granulation, necrosis, or intact. Periwound skin may include redness, warmth, swelling, normal, or eczema. Each of these three groups permits several values. “Hollowed” and “layer” are provisional labels from the source form; change them through a later migration if clinical review requires it.
- For v0.1 SQLite, these three groups are JSON arrays on Assessment. Application code validates the enum values and rejects duplicates on inserts and updates; direct SQL writes bypass that check. PostgreSQL is planned for the later full application, where these can become native enum-array columns.
- Infection is yes, no, or not recorded. It is not inferred from other findings. Length, width, and depth permit decimal centimetres; absent measurements remain null.
- Remarks adds to the existing observations, care performed, and expected outcome text fields; it does not replace them.
- Show the previous assessment's expected outcome beside a new form. Do not copy prior findings into new fields.
- Saved assessments are append-only. A wound is open when `closed_at` is null and closed when it has a server-recorded UTC timestamp. A closed wound cannot receive a new assessment until it is reopened by clearing `closed_at`; reopening preserves its history and allows new entries. Patients have no active/closed status or closure operation.

## Stays and case identity

The patient ID owns the wound history; the required name helps nurses identify the patient, and the generated reference remains a stable case reference. A stay connects exactly one patient and one establishment; both may have many stays over time. A stay with no end date is ongoing, and a patient has at most one ongoing stay. Room, bed, and service are free-text context on the stay, not separate records or unique assignments. Any number of patients may share an establishment, room, and bed.

Changing room, bed, or service updates the existing stay and leaves the patient record unchanged. A transfer ends the prior stay and starts one at the new establishment, preserving the patient ID and wound history. Earlier stays remain readable. The schema has a nullable patient `archived_at` for a future archive filter; current records are unarchived. Each new patient case gets its own ID and empty wound history.

Store one required patient name field, without splitting it into given name and surname. Do not add patient initials, patient addresses, hospital patient identifiers, or identity mappings. Patient names and birth dates must not be logged. Establishment contact information is separate from patient identity.

## Privacy and security

The [authentication contract](authentication.md) covers one locally
provisioned operator, email/password login, persistent server-side sessions,
immediate logout revocation, password recovery, and backend authorization for
one shared workspace. It includes Origin/CSRF protection and rate limits.
Local provisioning, login, session status/logout, default API protection, rate
limits, password recovery, and expired-credential cleanup are implemented.
The full lifecycle has been checked over local HTTP against an isolated database
and captured inbox. Keep that verification as a gate for clinical HTTP endpoints.

- Authenticate every care-data API. UUIDs are not access control. Auth ships before care-data HTTP routes.
- Credentials, session secrets, the runtime database, and private uploads stay out of Git.
- No analytics or external AI in v0.1. Do not log patient names, narratives, assessment bodies, room/bed values, credentials, or tokens.
- No case data in `localStorage`, IndexedDB, or service-worker caches.
- Photos are optional, one per assessment, stored privately and served only through an authenticated endpoint. Metadata stripping does not make a picture anonymous.
- Testing uses fictional cases and non-patient fixture images only.

## How work is completed

Land work as focused PRs. Done means merged to `main` plus verified scoped behavior. A schema migration or tested API is valid work even without a UI. Run the app at its current stage. Do not ship broken controls or defer security behind a public endpoint.

The app is implemented to learn Python/Flask. Agents explain, guide, and review unless explicitly asked to code, and then only the requested change.

## v0.1 exclusions

Android, PWA, native wrappers, camera capture, offline sync, AI/dictation/MCP, public hosting, PostgreSQL, Redis or background jobs, multi-user or role management, exports, general attachments, body maps, catalogues, pain scores, charts, clinical advice, image analysis, multi-photo editing, and saved-assessment editing. Docker packaging is optional and not a prerequisite for earlier PRs.

## Later, not now

Next: Android access to the same backend, which is the intended client. Then: AI-assisted entry that proposes editable fields the nurse must save. Later: authenticated MCP tools over the same application logic. No AI diagnosis or treatment recommendations.
